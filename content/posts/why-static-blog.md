去年年底，把博客从原来的动态框架迁移到 Astro 静态生成，是这类重构里常见的一步。本文以示例的口吻记录这类迁移通常的理由、坑和收获。

## 为什么考虑静态

常见的迁移理由有三个：

- **运维负担低。** 没有常驻进程，没有数据库连接。构建产物就是一堆静态 HTML，托管到支持静态站点部署的平台（例如 Cloudflare Pages）上，需要日常照看的部分明显更少。
- **攻击面更小。** 页面在构建时生成，线上没有响应请求时执行的服务器端应用代码，SQL 注入这类典型服务端注入路径也就不适用。这不等于"绝对安全"——托管平台、构建流程、依赖与引入的客户端脚本仍然是需要关注的面，只是需要看护的代码路径变少了。
- **渲染路径简单。** 首屏就是完整的 HTML，没有客户端水合过程，这通常对加载性能有利；实际指标取决于托管、内容体积和访问者网络，示例里不做具体承诺。

> 有人会说静态站"功能受限"。但仔细数一下博客真正需要的功能：文章、标签、搜索、RSS、评论。前三样构建时就能解决，剩下两样各有成熟的外包方案。

## 迁移过程中常见的坑

迁移并不全是顺心的。这类迁移里比较典型的几个：

| 问题 | 原因 | 解法 |
| --- | --- | --- |
| 中文标题 URL 过长 | 文件名直接做 slug | 改用英文文件名 + 保留中文标题 |
| 旧链接 404 | 路由结构变了 | 逐条配 `_redirects`，保留旧路径 |
| 搜索体验下降 | 原方案依赖服务端 | 换成 Pagefind，构建后索引 |

## 配置长什么样

静态站的核心配置可以很小。以 Astro 为例，一个能跑起来的 `astro.config.ts` 通常只需要十几行：

```ts
// astro.config.ts
import { defineConfig } from "astro/config";

export default defineConfig({
	site: "https://example.com",
	markdown: {
		// 构建时高亮，不带客户端开销
		shikiConfig: {
			themes: { light: "github-light", dark: "github-dark" },
		},
	},
	integrations: [],
});
```

路由按目录生成，Markdown 文件放进 `content/`，构建工具负责其余部分。

## 写作体验往往更好

这类迁移最常见的收获是写作摩擦变小。原来发一篇文章要经过后台登录、编辑器、预览、发布几个环节；现在就是写一个 Markdown 文件，`git push`，由托管平台的流水线自动构建部署（构建时长视平台与内容而定）。环节越少，拖延的借口就越少。

## 还值得继续用下去吗

对以文字为主的个人博客来说，静态架构通常是合理的选择。唯一的"遗憾"（示例语境下）是这类迁移往往没有更早做——花在维护旧框架上的时间，本可以用来多写文章。如果你也在犹豫，建议先估算现在每月花在"让博客活着"上的时间，再做决定。
