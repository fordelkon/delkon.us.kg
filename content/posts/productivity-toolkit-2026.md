每年我都会折腾一批新工具，绝大多数在试用期结束前就被淘汰了。这篇示例笔记以常见的筛选标准（用满三个月以上、"没有它会觉得别扭"）盘点一批留得下来的工具——文中经历为虚构示例，用于排版预览，不代表站长真实使用情况。

## 留下来的

**终端里的 fuzzy finder。** `fzf` 配合 shell 历史搜索，常被列为对日常习惯影响最大的一类小工具。搜历史命令不再靠 `history | grep` 猜关键词：

```sh
# Ctrl-R 现在是模糊搜索，支持多关键词
git checkout <C-r> fix header offset
```

**扁平化的任务清单。** 试过嵌套层级、试过标签体系，最后留下的反而是单层清单加每日三条的规则。结构越复杂，维护清单本身就越像一项工作。

**本地优先的笔记。** 笔记存成纯文本文件放进 git 仓库，编辑器就是编辑器，没有私有格式锁定。真正的收益在于：搬家零成本，grep 即搜索。

## 每周留一个复盘窗口

为了避免工具清单越积越长，可以每周固定检查三件事：

- 哪个工具这周真正帮忙完成了一项工作？
- 哪个快捷键需要反复查找，是否值得保留？
- 哪个自动化流程失效了，修复成本是否值得？

## 被淘汰的候选者

| 工具 | 淘汰原因 |
| --- | --- |
| 某知名任务管理应用 | 订阅费高，且项目视图多于任务本身 |
| 自动化剪贴板工具 | 触发热键太多，反而打断心流 |
| 时间块规划应用 | 排得越满，越容易整块崩掉然后弃用 |

> 工具评估里最难的一课：试用期里觉得"好新潮"的东西，三个月后还愿意打开的，一年下来通常不超过两件。

## 一条检验标准

判断一个工具是否真的融入了工作流，我会问一个问题：**它出问题的时候，我是修复它，还是直接绕过它？** 绕过的工具就删掉。留下来的那几件，都是故障时会认真修复的——这就是全部的筛选逻辑。
